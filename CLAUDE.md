# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**LIGHTS OUT** — a first-person horror maze game. Unity 6 (editor `6000.6.2f1`), URP. It started life as the "Unity Essentials" / Get Started tutorial (a third-person robot collecting stars); the tutorial content has been removed, but the robot and Starter Assets controller are still the player. The game is now: you are dropped into a dark procedural maze with a flashlight, you collect 5 stars while something hunts you, and then you have 60 seconds to find the escape hatch.

Not a git repository. There is no test suite and no assembly definitions under `Assets/`, so all game code compiles into `Assembly-CSharp`.

## Commands

Development happens in the Unity Editor (Rider / Visual Studio / VS Code attach via `.vscode/launch.json`). The generated `*.csproj`, `*.sln`, `Library/`, `Temp/`, `obj/` and `Logs/` are Unity-generated — do not edit them.

Batch-mode compile check / build:

```
"C:\Program Files\Unity\Hub\Editor\6000.6.2f1\Editor\Unity.exe" -batchmode -quit -projectPath "D:\Unity\essentials\My project" -logFile -
```

Compile errors from the running Editor also land in `Logs/Editor.log` — `grep "error CS" Logs/Editor.log` is the fastest way to check the last compile without launching a second Unity instance (one is usually already running and holds the project lock).

Only scene in build settings: `Assets/Scenes/GetStarted_Scene.unity`. No tests exist; if added, run with `-runTests -testPlatform EditMode|PlayMode` (and `-testFilter <name>`).

## The one thing to understand first

**Almost nothing is authored in the scene.** `MazeGenerator.Awake` (`[DefaultExecutionOrder(-100)]`) builds the entire game at runtime: walls, floor, ceiling, the NavMesh bake, the stars, the first-person rig, the flashlight, and every director component, each `AddComponent`-ed onto the `MazeGenerator` GameObject and wired with a `Configure`/`Bind` call. The main authored piece is **the shop room**: a `ShopRoom` object at (−92, 5, −45), west of the maze, that is real scene geometry you can select and edit. It is generated once by the editor menu item **LIGHTS OUT > Build > Shop Room** (`Assets/Editor/ShopRoomBuilder.cs`; materials in `Assets/SourceFiles/Materials/Shop`). **F78:** the room is a 9 × 12 × 3 m alchemist's shop dressed from the `Assets/BK_AlchemistHouse` pack (architecture scaled ×1.2, every prop placed by renderer bounds because many pack pivots are off-centre, pack colliders/rigidbodies stripped in favour of builder-made `BoxCollider`s, 7 lights max); the dressing passes and a `ShopRoomBuilder.Audit(root)` self-check live in the `partial` file `ShopRoomBuilder.Dressing.cs`, `ShopRoomBuilder.BuildSilently()` rebuilds without dialogs, and `AlchemistMaterialUpgrade` (`Assets/Editor/AlchemistMaterialUpgrade.cs`, idempotent, no menu item) is the pack's one-off Built-in → URP conversion, run automatically by every builder that uses the pack. Spec: `plannings/shop-room-alchemist-plan.md`. The salesman is the **Guard** from the Adam Character Pack (idling on the pack's `Guard_AnimationController`, two emissive eye beads on its head bone); `ShopRoom.headPivot` is its Humanoid Head bone, turned in `LateUpdate` as a yaw offset on top of that frame's animated pose (a plain non-animated pivot still works). Without it `MazeGenerator` logs an error and clearing floors 1–4 falls back to a plain win. **Leaving the shop (F84)** mirrors the hatch walk-in: E at the door → `ShopRoom.WalkOutRoutine` freezes the player, swings the leaf out on `ShopRoom.doorHinge` (a pivot on the leaf's edge made by `ShopRoom.CreateDoorHinge`; the builder wires it, and an older scene without it gets one at runtime from `Door/WoodDoor01…`), eases the player up to the doorway looking through it, then on through it while the screen and the shop hum fade out → `GameFlow.NextFloor()`. The swing direction is picked at runtime so the leaf always opens away from the room. No leaf at all = the old plain fade (`DescendRoutine`). **The leaf must not be Static** — the shop room is otherwise all-static, and static batching merges a static leaf into a combined mesh at scene load, after which the hinge turns but nothing moves on screen. `ShopRoomBuilder.MakeMovable` clears the flags on the hinge; Check Project flags a static leaf and Build Missing Pieces fixes it in place. The same applies to anything else in an authored room that has to move at runtime. **The pack's `Architecture/Door` model is the frame and a closed panel fused into one mesh** — it can never open and it hides the `WoodDoor01` leaf, so the builder only uses it to measure where the leaf goes and then deletes it (the `IntWall01door` wall module already frames the opening); Check Project flags a leftover one and Build Missing Pieces removes it. `IsInShop` stays true through the walk-out (cleared by the reload), so the maze HUD doesn't pop back up mid-walk.

Another authored-once piece is **the interactables gallery** (F72/F73/F74/F75): an `InteractableKit` object holding one live instance each of the shutter door, wall button, battery cell, fuse box, and (F74) the bottle/can throwables, glass/puddle noisy-floor patches, lantern, lore note and the four theme interactables (call bell/steam valve/candles/terminal), plus (F75) **the Stalker** — the player's own robot body (`Assets/Prefabs/PlayerRobot.prefab`), instantiated, unpacked and stripped down to its visuals — that `MazeGenerator.BuildDoors`/`BuildFuses`/`BuildThrowables`/`BuildNoisySurfaces`/`BuildLantern`/`BuildLoreNotes`/`BuildThemeInteractables`/`BuildStalker` clone for every maze. Generated once by **LIGHTS OUT > Build > Interactables** (`Assets/Editor/InteractableKitBuilder.cs`, build-missing-only by default — each slice only adds its own slots). Without it, or with a slot missing, `MazeGenerator` logs an error naming the menu item and skips just that feature for the run (doors/buttons/vaults, fuses, throwables, noisy floors, the lantern, notes, theme interactables, or the stalker — whichever slot is missing).

The second authored piece is **the floor-theme gallery** (F41): a `FloorThemes` object north of the maze at (−70, 5, −6) with one `FloorTheme` row per floor, each holding live prefab instances of that floor's wall, pillar, floor tile, ceiling tile, lamp, locker and props. Generated once by **LIGHTS OUT > Build > Floor Themes** (`Assets/Editor/FloorThemeBuilder.cs`; assets under `Assets/SourceFiles/Themes/<n>_<Name>/`, never overwritten on a rebuild unless you choose *Replace everything*). At Play, `MazeGenerator.ResolveTheme` picks the row for `FloorProfile.ThemeIndex` and **clones the scene instances** (so unapplied overrides count), then deactivates the gallery. Without it, or with an incomplete row, it logs an error and builds the old primitive maze. Look owns colour, fixtures and prop density (`FloorTheme`); gameplay numbers such as lamp intensity and range stay in `FloorProfile`. Spec: `plannings/floor-themes-plan.md`.

So: **do not look for Inspector wiring or prefabs to explain behaviour, and do not add setup to the scene.** Read `MazeGenerator.SetUpAtmosphere` (near the end of the file) — that method is the composition root. New systems get created and configured there.

Execution order matters and is set explicitly:

| Order | Component | Why |
|-------|-----------|-----|
| −100 | `MazeGenerator` | builds everything before anything else's `Awake` |
| −90 | `FirstPersonRig` | camera/flashlight exist before directors look for them |
| −85 | `TensionDirector` | its counter is created before the title screen, so it draws *underneath* it |
| −84 | `PlayerHud` | builds the resource HUD before `TouchControls` sits above it |
| −83 | `TouchControls` (F76) | above the HUD, below the (lazily-built) menu panels; drives `TouchInput.Poll()` every frame |
| −80 | `MainMenu` | freezes the clock (`Time.timeScale = 0`) until the player presses Start |
| −50 | `HorrorAtmosphere` | ambient/fog/skybox blackout after the world exists |

## Run lifecycle

0. **START GAME (F86)** opens the **Intake** (`IntakeRoom`, a short authored tutorial room) instead of the rules screen: `MainMenu.BeginNewCampaign` → `CloseMenus()` → `IntakeRoom.Begin()`, `GameFlow.IsInIntake = true`, the run is NOT active (hunter held in `AIFollower.Update`, everything else gated on `IsRunActive`). Nine steps (look, move, torch, focus, battery, read, throw, hide, star + hatch), one goal at a time on a top-centre **objective card** (OBJECTIVE label + `n / 9`, the goal in caps, key-cap chips via `TouchInput.Key` so touch shows button names, a tick then fade between goals) plus a bobbing amber **goal arrow** over the target and a pulsing glow on pickups (`IntakeRoom.goalArrow`/`goalGlow`, authored by the builder; one shared light); the hatch walk-in or the pause menu's SKIP TUTORIAL ends it: blackout → back to the maze start cell → `IsInIntake = false` → `GameFlow.BeginRun()`, i.e. step 1 below. CONTINUE, Retry, START NEW MAZE and NEXT FLOOR never enter it (they go through `SkipMenuOnLoad` → `StartGame`). With no `IntakeRoom` built START GAME falls back to the old rules screen (now also reachable from the title's CONTROLS button, as a reference sheet).
1. `MainMenu` opens with `Time.timeScale = 0`; `StartGame` unfreezes and calls `GameFlow.BeginRun()` (sets `GameFlow.RunStartTime` and `GameFlow.IsRunActive = true`).
2. `Pickup.OnTriggerEnter` (Player tag) → static `Pickup.OnCoinCollected` → `GameManager` decrements and raises `GameManager.ProgressChanged(collected, total)`.
3. Last star → `GameManager.AllStarsCollected`. **If anything is subscribed, that listener takes over**; only with no listener does `GameManager` call `GameOutcome.FloorCleared` directly. `MazeEscape` and `TensionDirector` both subscribe.
4. `MazeEscape` opens a glowing hatch at least 12 m away, starts a 60 s countdown, and builds a landing platform underneath it.
5. Ending, always through `GameOutcome`:
   - reach the hatch on floors 1–4 → `MazeEscape.DropThroughHatch()` then `GameOutcome.FloorCleared()`: blackout during the fall, teleport into `ShopRoom`, a payout ledger, CONTINUE → `GameFlow.IsInShop = true` until the player walks through the door (E) → `GameFlow.NextFloor()`.
   - reach the hatch on floor 5 → `GameOutcome.Win()` — the ending, with the campaign total.
   - timer expires → `GameOutcome.Lose(LoseReason.OutOfTime)`
   - hunter catches you → `AIFollower.PlayerCaught` → holding a Second Wind, `GameOutcome.SecondWindSequence` (cut to black, hunter warped away and stunned, player freed) instead; otherwise `GameOutcome.Lose(LoseReason.Caught)` → `CaptureSequence` coroutine (camera eases onto its eyes, torch flickers out, blackout) → end screen.

`GameOutcome` is single-shot: `IsOver` / `IsEnding` guard every entry point, so a hatch drop landing mid-capture is ignored.

## Systems

- **World** — `MazeGenerator` (~790 lines): seeded maze, runtime `NavMeshSurface` bake, star placement, actor placement, and the composition root described above. `UsedSeed` is the seed actually used (Inspector `seed`, a pending retry seed, or `Environment.TickCount`); it is logged and shown on the end screen. **Kit maze (F48):** when `GameFlow.UseKitMaze` is set, `BuildGeometry` takes a third branch — `BuildKitGeometry`/`BuildKitPillars` assemble the maze from the Maze Modular Puzzle Kit (`Assets/Maze/Prefabs`) instead of `FloorThemes`, reading prefab references off a `KitMazeTheme` scene object built by **LIGHTS OUT > Build > Kit Maze Theme** (`Assets/Editor/KitMazeThemeBuilder.cs`). `_theme` stays `null` in this mode, so the ceiling, lockers, wall lamps, props and atmosphere all keep taking their existing primitive branches. Cell size, wall thickness and wall height are overridden to 5 m / 0.4 m / 3.9 m to fit the kit's 3/2/1 m wall pieces exactly; floors are filled by the recursive square tiler `TileFloorRect`, walls by the greedy 3/2/1 span filler `FillSpan`. Missing or incomplete theme → `LogError` and fall back to the normal maze, mirroring `ResolveTheme`. The title screen's second button, START NEW MAZE, calls `GameFlow.StartKitMaze()`; the flag lasts the whole campaign (Retry and the next floor both stay in kit mode) until `GameFlow.ReturnToMenu`. Spec: `plannings/kit-maze-plan.md`. **Maze dressing (F70):** a private `MazeDressing` view, resolved once by `ResolveDressing()` right after `ResolveKitTheme()`, is what every prop/decal/set-piece pass reads (never `_theme`/`kitTheme` directly) — themed floor → `_theme`'s dressing fields; kit mode → `kitTheme`'s common dressing with wall/ceiling prop chances forced to 0 (the kit set never gets themed wall/ceiling props); primitive fallback → all-default (empty), so an un-rebuilt scene spawns nothing new. Five new passes, each its own RNG offset from `usedSeed` so the existing carve/star/lamp/locker/prop/shard streams (+0…+5) are untouched: `BuildSetPieces` (+8, pre-bake — reserves its cell, and `_propWalls`/`_setPieceCells` bookkeeping so wall/ceiling props skip it), `BuildKitDressingPreBake` (+9, kit-only gates + trees, also pre-bake since both carry colliders), `BuildKitWallLights` (+10, kit-only, post-bake emissive wall overlays), `BuildFloorProps` (+6, post-bake, collider-less floor clutter) and `BuildDecals` (+7, post-bake, alpha-clipped analytic-placement quads — no raycasts). **Blood decals (7 Oct 2026):** the code-drawn blood splat/smear/pool textures are replaced by `Assets/Blood decal pack` (its own materials are Built-in shaders, so only the textures are used). `BloodDecalUpgrade` (`Assets/Editor/`, idempotent, runs at the end of Build > Floor Themes and Build > Kit Maze Theme, flagged by Check Project) makes one transparent URP Lit material per texture under `Themes/Common/Materials/BloodPack`, switches the shared `BloodSplat`/`BloodSmear`/`BloodPool` materials in place, and adds a `DecalVariants` component (materials + aspect ratios) to every `*_Blood*` prefab; `BuildDecals` → `ApplyDecalVariant` picks one by a hash of `(x, z, i, wall/floor)` — no rng draw, so the +7 stream is unchanged — and reshapes the quad so the variant's longest side equals the placed size. Density is `MazeGenerator.decalDensity` (×2: theme chances capped at 0.9, +1 decal per cell) and `bloodWeight` (×3 pick weight for pieces with `DecalVariants`) — both only change the +7 decal stream. **Set-piece wall decals:** `BuildSetPieces` puts a set piece's pivot ON the wall face with +Z into the cell, so a set piece's wall decal goes at `FloorThemeBuilder.WallDecalInset` (0.02), not the old 1.98 that hung them 2 m out in mid-air; `SetPieceDecalFix` (same hooks as `BloodDecalUpgrade`) re-seats old prefabs and reshapes their shared-blood quads to the texture's aspect. **No footprints** (7 Oct 2026): the builder no longer makes `*_Footprints` decals and `BloodDecalUpgrade` turns old ones into blood pools (free roll). **Corpses:** the shared `FallenRunner` set piece's capsule body is replaced by the six `Assets/DeadBody LITE/Prefabs/Body_Only` bodies (`CorpseUpgrade.AddBodies`, used by the builder and to migrate the existing prefab; laid along the wall, seated by renderer bounds, pack rigidbodies stripped, box colliders kept); one is active per placement via `ModelVariants`, applied in `BuildSetPieces` by a cell hash (no rng draw, +8 stream unchanged). Only the pack files the game references are in git (force-added; both pack folders are otherwise ignored — see `.gitignore`). Transparent decal materials must keep `_BlendModePreserveSpecular` = 0: URP re-validates it to premultiplied alpha otherwise and the torch's specular lights the whole quad as a pale rectangle. Built by **LIGHTS OUT > Build > Floor Themes** (now `FloorThemeBuilder` split across `FloorThemeBuilder.cs` and the `partial` file `FloorThemeBuilder.Dressing.cs`, which holds the shared texture/decal/particle helpers and the common prop/set-piece/dust set) and **LIGHTS OUT > Build > Kit Maze Theme** (`KitMazeThemeBuilder`, which calls `FloorThemeBuilder.BuildCommonDressing()` for its share of the same common set). Re-run both (Keep existing assets) and save the scene to get the new content; an un-rebuilt scene plays exactly as before. Spec: `plannings/maze-dressing-plan.md`. **Darkness pass (F71):** the per-floor lamp/fog/ambient numbers live in `FloorProfile.For` (`CellsPerLamp` Blend(5,8), `LampIntensity` (1.0,0.7), `LampRange` (5.0,4.0), `Ambient` scalar (0.015,0.006), `FogDensity` (0.07,0.12)) and apply to the kit maze and the primitive fallback directly — but a **themed** floor (1–5 normally) reads `_theme.Ambient` instead (`ResolveTheme`), so the scene's `FloorTheme.ambient` rows need their own pass: `DarknessRelight` (`Assets/Editor/DarknessRelight.cs`, no menu item) scales every `FloorTheme.ambient` down so its brightest channel is 0.012, via `SerializedObject` (idempotent — a row already at or under the target is left alone). It runs automatically at the end of **LIGHTS OUT > Build > Floor Themes**; after a hand edit to `FloorTheme.ambient`, **LIGHTS OUT > Check Project** flags it and **Build Missing Pieces** relights it. Lamp fixture emission dropped to `lampColor * 1.2` (star stays at `* 2.5` so it still reads as the thing worth finding); stars also pulse ±30 % at 0.5 Hz (`StarPulse`, attached in `AttachStarLight`). **Doors, buttons & vaults (F72):** `MazeGenerator.BuildDoors` (+11 for placement, +15 for vault loot; runs post-bake, after `SpawnStars` and before `SpawnShards`) clones `InteractableKit`'s `shutterDoor`/`wallButton`/`batteryCell` templates. Security-door candidates are found by BFS: `ReachableCells(start, blocked)` treats one passage as closed and checks whether the start side then loses a star cell — only a bridge passage (the maze is braided by `RemoveDeadEnds`, so most aren't) qualifies, preferring a 3–40 % cut-off region. Its button lands ≥3 BFS steps into the start-side component (`BfsWithin`), on a free wall not already in `_propWalls` and not near a lamp (`IsLampWall`, a proximity check — lamps aren't indexed by cell/wall). Because the maze is braided, bridge passages are rare and that search often places nothing, so both passes fall back to **sealing a cell**: a shutter on every opening of a star's own cell (or, for a vault, a two-opening cell), accepted only if `ReachableCellsAvoiding(start, cell)` still reaches every other cell. The shutters are chained through `MazeDoor.LinkedDoor` (one-way; `Unlock` propagates), and one button opens the whole chain. The timed conversion walks the chain too, so a timed star room rolls down together. A vault is a dead-end cell (`WallCount == 3`), or that sealed-cell fallback, turned into the same kind of locked room, plus a `BatteryCellPickup` and 2 of the floor's own shards forced inside via `_vaultForcedShardCells`, read by a modified `SpawnShards`/`BuildShard` (shard count and caps unchanged — the forced ones are subtracted from the normal pool, not added). Manual doors gate nothing; `FloorProfile.ManualDoors`/`SecurityDoors`/`Vaults`/`HasTimedDoor` are per-floor tables like `Footprints`. Missing/incomplete `InteractableKit` → `LogError` naming **LIGHTS OUT > Build > Interactables**, and doors/buttons/vaults are skipped entirely (no primitive fallback, per decision D11). Spec: `plannings/darkness-and-interactivity-spec.md`, slice F72. **Objectives, fuses & hatch variants (F73, flags since F77):** `FloorProfile.Objectives` (`[Flags] enum Objective { None = 0, Lockdown = 1, Blackout = 2, KeyHunt = 4 }`, tested with `FloorProfile.Has(Objective)`) is the floor's mechanic *set*, not a single value — floor 1 is always `None` (stars only, the teaching floor); every floor from `FirstRolledFloor` (2) on rolls exactly `MechanicsPerFloor` (2) of the three from the seed (`FloorProfile.RollObjectives`, a pure function of `(UsedSeed, floor)` salted apart from `RunRules`' own roll so a Retry keeps its pair and the two rolls never correlate), excluding whatever pair `GameFlow.RolledObjectives[floor - 1]` was so two consecutive floors are never identical. `Has(Blackout)` sets `FuseCount = 3` and knocks 2 off `StarCount`; `Has(KeyHunt)` sets `KeyCount` (2 on floors ≤3, else 3) and knocks 1 off; both trims share one final `Max(2, StarCount)`. `Has(Lockdown)` sets `HasTimedDoor` (folding in the old `HasTimedDoorTable`). `MazeGenerator.debugObjectives` (Inspector, a flags mask) forces a floor's pair for testing, bypassing the roll (and not writing `RolledObjectives`) — `None` means "roll normally". **Key Hunt (F77):** on a `KeyHunt` floor, `MazeGenerator.BuildKeys` (+18, post-bake, after `BuildFuses` and before the +13 throwable/notes passes) scatters `KeyCount` brass keys (`KeyPickup`, cloned from `InteractableKit.keyPickup`) on free walls, the same decreasing-`minSeparation` placement loop as `BuildFuses`. `KeyRing` (an *instance* component on the player, same pattern as `ThrowController` — see the Player bullet) is the single source of truth for `Held`/`Total`/`Changed`; its `Total` comes from however many keys actually got placed (decision: gate on what was placed, not `FloorProfile.KeyCount`), so an undersized maze still locks behind what it could fit. `MazeEscape` is `Locked` for the whole escape when `KeyRing` is incomplete: a Hatch's trigger does nothing but play a padlock clunk and show `LOCKED · h / t KEYS` (at most every 2 s); a Lift's ring fills nothing and shows `LIFT LOCKED · h / t KEYS`. While locked the escape ping/chevron retarget to the nearest missing key (`KeyRing.TryNearestMissing`) instead of the hatch, and the hatch/lift light + glow material turn red (`MazeEscape.ApplyLockLook`, same red language as a fuse box's indicator) until `KeyRing.Changed` reports `IsComplete`, at which point a `"THE HATCH/LIFT IS UNLOCKED"` subtitle shows and the normal path resumes — `CompleteEscape` is still the single exit. Keys are deliberately neither a `Pickup` nor an `ObjectiveToken` (see the Gotchas entry below): they never gate the hatch *opening*, only its use. `TensionDirector` appends a third `KEYS h / t` counter segment when `KeyRing.Total > 0`; Fuse Map (shop item) also beacons every key and the Star Compass points at untaken ones. `FloorIntroBanner`'s objective line is now built from a list (`FIND n STARS`, then `RESTORE n FUSES` / `FIND n KEYS FOR THE HATCH` / `SECURITY LOCKDOWN` for whichever mechanics are set), joined with ` · `. Spec: `plannings/key-hunt-plan.md`. `MazeGenerator.BuildFuses` (+12, post-bake, after `BuildDoors`) scatters `FuseCount` fuse boxes (far apart, off the start/star/door/vault cells, on a free wall like a button), then runs a **multi-source BFS from every fuse cell at once** so every cell (and, via a parallel `_lampCells` list, every lamp) belongs to whichever fuse reached it in the fewest steps. On a Blackout floor every lamp starts `SetPowered(false)` and the start cell gets one static red emergency light; a `FuseBox` (`IInteractable`, hold 2 s) powers its whole sector back on in a ripple (`WallLamp.SetPowered(true, steps * 0.12s)` per lamp) and completes an `ObjectiveToken` (see the Escalation bullet). `AIFollower.BindTorch(Flashlight, Transform camera)` (wired in `SetUpAtmosphere`) makes the hunter notice the torch beam itself landing on it (angle/range/LOS against the beam's own blended shape, 6 s cooldown, `HearNoise` 40 m) even without full sight. `MazeEscape` (+17, seeded off `UsedSeed` alone so a retry keeps its choice) makes floors 3–5 a 50 % chance of a **Lift** instead of a Hatch: an 8 s-to-fill 2 m ring (decays at half rate outside it, HUD `LIFT ARRIVING n%`, first entry `HearNoise` 60 m) that completes through the exact same `DropThroughHatch` → `GameOutcome.FloorCleared`/`Win` path as the Hatch trigger. **Stealth tools, lore, theme interactables, run rules (F74):** all post-bake, after `BuildFuses`. `BuildThrowables`/`BuildNoisySurfaces` share one `+13` stream (`ThrowableItem`/`NoisySurface` clones on plain cells); `BuildLoreNotes`/`BuildThemeInteractables` share `+14` (2 notes per floor, ids `(floor-1)*2 + {0,1}`, text verbatim in `plannings/darkness-and-interactivity-spec.md`; theme interactables keyed off `FloorProfile.ThemeIndex` — Ward→call bell, Boiler→steam valve, Crypt→candles ×2, Lab→terminal — skipped in kit mode and on the primitive fallback); `BuildLantern` is `+15` (its own `System.Random`, sharing only the numeric offset with `BuildDoors`' vault-loot stream, never the same instance). All four wall-mounted kinds share `TryPickFreeWallCell`/`TryPlaceOnFreeWall`, the same free-wall test `PlaceButtonFor`/`BuildFuseBox` use. `RunRules` (static, `Resolve(usedSeed, floor)` hashed so a retry keeps its floor's rule, floor ≥ 2) is resolved inside `ApplyFloorProfile` — before its `useFloorProfile`-off early return — and `ApplyToProfile` mutates the already-blended `FloorProfile` fields (`HearingScale`, `FogDensity`/`ViewDistance`, `PhantomInterval`, `ShardCount`/`WalkSpeed`) right after `PlayerInventory.ApplyActiveModifiers`; effects with no home on the profile (`DyingGrid`'s 60 s lamp kill via a `MazeGenerator` coroutine, `WeakBattery`'s `Flashlight.SetStartFraction`/`SetRechargeMultiplier`, `GlassFloors`' `NoisyPatchMultiplier`, `KeenEars`' `ShardPayoutMultiplier` read by `PlayerWallet.CollectMazeShard`, `Restless`'s `DreadDirector.SetHardMinimumCooldownMultiplier`) are read straight off `RunRules` by whichever system needs them. `FloorIntroBanner` (RuntimeUi, built/`Show`n last in `SetUpAtmosphere`) waits out the title screen itself (polls `GameFlow.IsRunActive` on unscaled time) before its 5.5 s fade-in/hold/fade-out.
- **Player** — `FirstPersonRig` builds the camera and head-mounted `Flashlight` (F key, flicker, `InputEnabled` so endings can take the torch away). **F71 darkness pass:** the beam is wide by default and narrows/brightens to a focused beam while RMB / gamepad LT is held (`IsFocused`, `FocusBlend` 0..1, eased over 0.15 s of scaled `Time.deltaTime`); `Range`/`OuterAngle` always return the current blended value, so anything testing "is X in the beam" stays correct mid-blend. Focused drain is ×1.5 (`focusedDrainMultiplier`); `SetRangeMultiplier(float)` is a hook for the Focus Lens shop item (F75, unused so far) that scales only the focused end of the range blend. The battery is no longer a one-shot resource: while off (or dead) for more than 2 s it recharges 1 s of charge per 3 s off, capped at 60 % (never fully, so a Spare Battery still matters), blocked while `GameOutcome.IsOver`; `IsDead` therefore clears itself once recharge brings `SecondsLeft` back above zero — don't cache "dead" as permanent. `Drain(float fraction)` removes battery directly (F75's Stalker touch). `PlayerStealthState` derives `NoiseRadius` from actual `CharacterController` velocity and exposes `VisibilityMultiplier` (driven by the torch: `TorchVisibility`, written every frame by `Flashlight` from its focus blend, `Lerp(0.85, 1.25, FocusBlend)` — a focused beam is more telling than a flat 1 used to be). ## Editor menu (LIGHTS OUT)

Every authored scene piece is generated by an editor menu item. The menu is organised so nobody has to remember what was run:

| Path | What it is |
|------|-----------|
| **Check Project** | Read-only report: each piece OK / FIX, with the menu item that fixes it. Run this first when unsure. (`Assets/Editor/ProjectSetup.cs`) |
| **Build Missing Pieces** | Runs only the builders whose piece is *missing*, in dependency order. Never rebuilds something that exists. |
| **Build > …** | One builder per scene piece (Floor Themes, Kit Maze Theme, Interactables, Phrase Books, Shop Room, Intake Room, Hunter Body). Re-running one deliberately rebuilds that piece. **Build > Re-skin Templates > …** empties specific `InteractableKit` slots and rebuilds just those. |
| **Debug > …** | Dev helpers that touch no content (Delete Save). |

Rules when adding or changing editor tooling:

- **A builder is the recipe for a scene piece — keep it** and put it under `LIGHTS OUT/Build/` (priority 100+). Give it a dialog-free `BuildSilently()` entry point (or make `Build()` dialog-free when the piece is missing), and **register it as a `Piece` in `ProjectSetup.Pieces()`** with a `Problem` check (missing/incomplete) and a `Build` action, in dependency order. A builder that isn't in `ProjectSetup` will be forgotten.
- **A one-off migration** (convert materials, patch existing scene data to a new format, clean up imports) **is not a permanent menu item.** Prefer running it automatically from the builder(s) that depend on it (as `AlchemistMaterialUpgrade` and `DarknessRelight` now are), or add a `Problem` check so Check Project flags it. If it really must be a menu item, put it under `LIGHTS OUT/Migrations/`, and **delete it (the menu item, and any code nothing else calls) once it has been applied to the scene and committed** — git history keeps it. Before deleting, confirm in the scene YAML that it was applied, and check no builder still calls into the file.
- Never auto-save the scene from a builder; mark it dirty and tell the user to save (Ctrl+S).
- Menu paths are referenced in log/`LogError` messages and comments as `LIGHTS OUT > Build > X` (`&gt;` in XML docs) — keep them in sync when renaming.

## Gotchas that bite

- **Statics must survive a scene reload and must not survive Play mode.** `GameFlow` and `GameOutcome.IsOver` both have a `[RuntimeInitializeOnLoadMethod(SubsystemRegistration)]` reset, because with *Enter Play Mode > Reload Domain* disabled a stale `SkipMenuOnLoad` would skip the title screen on the next run. `GameFlow.IsInShop`, `PlayerWallet` and `PlayerInventory` all have the same reset, and are also cleared in `GameFlow.ReturnToMenu` — the economy lives for one campaign only. `GameFlow.UseKitMaze` (F48) follows the same rule: reset in `ResetStatics` and cleared in `ReturnToMenu`, since it is meant to last a campaign, not a Player session. Any new static run state needs the same treatment.
- **`ShardPickup` is deliberately not a `Pickup`.** `GameManager.Start` counts `Pickup` objects as stars; a shard sharing that type would corrupt the star count and could fire `AllStarsCollected` early. **`ObjectiveToken` (F73) is the same idea for non-star objectives** (fuse boxes) — `GameManager` counts it alongside `Pickup`s in a second tally, so it gates `AllStarsCollected` too without touching the star count itself. **`KeyPickup` (F77) is neither** — a key never gates the hatch *opening* (it still opens on the last star/fuse exactly as before), only its *use*; the lock lives entirely in `MazeEscape`, not `GameManager`.
- **A `WallLamp.SetPowered(false)` lamp is not `IsDead`.** They're independent: unpowered just means dark-and-not-ticking-its-flicker right now (a Blackout floor before its fuse), `IsDead` means permanently killed (F27). `DreadDirector`'s kill waves/breath-blink and `PhantomDirector`'s lamp-blink phantom all check `IsPowered` too, or they'd waste a blink on a lamp that's already invisible. `Kill()` on an unpowered lamp is allowed and just waits — the fade plays once the lamp is powered back on.
- **Every static-event subscriber unsubscribes** in `OnDestroy`/`OnDisable` (`GameManager`, `MazeEscape`, `TensionDirector`, `HorrorAudioDirector`, `GameOutcome`). Restart is a plain `SceneManager.LoadScene`, so a missed unsubscribe leaks across reloads. Keep the pattern. `DoorBreakers` (F75) follows the same registry pattern as `LightPool`: scene-scoped, `SubsystemRegistration`-reset, and every registrant (`AIFollower.OnDisable`, `Stalker.OnDestroy`) unregisters itself.
- **`Time.time` is the run clock** and stands still at `timeScale = 0`, which is why run time is net of menu and pause. Don't swap it for `Time.unscaledTime`.
- **The cursor fight.** `StarterAssetsInputs` re-locks the cursor on every focus change, so anything showing a menu calls `PlayerLock.SetCursorFree(true)` *every frame*, not once. Freezing the player is three flags (`MovementLocked`, `LockCameraPosition`, `cursorLocked`) — always go through `PlayerLock.Freeze`.
- **Capture needs sight, not just distance.** A bare radius test captures through a wall (two actors either side of a 0.5 m wall are ~1.5 m apart), and `Update` still ticks at `timeScale = 0` behind the title screen — hence the `GameFlow.IsRunActive && _hasSight` gate in `AIFollower`.
- **`GameManager` counts stars at `Start`.** Anything spawning or removing stars after that desyncs the count.
- **Input System only** (`activeInputHandler: 1`). Keep the `#if ENABLE_INPUT_SYSTEM` guards in `ThirdPersonController` / `StarterAssetsInputs`. Note `Flashlight` and `PauseMenu` read `Keyboard.current` / `Gamepad.current` directly and bypass the action map, so those bindings are not remappable yet — as of F71 that now includes `Mouse.current.rightButton` / `Gamepad.current.leftTrigger` for the focused beam.
- **`Flashlight.IsDead` is no longer permanent (F71).** It recharges while off and can clear itself mid-run, so don't cache "the torch is dead" past one frame — re-read `IsDead`/`Charge` each time, the way `PlayerHud.UpdateBattery` already does.
- **A door is built post-bake with a collider and deliberately no `NavMeshObstacle` (F72).** The navmesh is already baked by the time `MazeDoor` exists, so a shutter can be any width the corridor needs — but it also means a `NavMeshAgent` has zero physics response to its collider and will silently clip straight through a closed door unless the door notices and opens itself (`MazeDoor.CheckHunterBash` + `AIFollower.Stall`). Any future door-breaker (F75's Stalker) needs the same self-detection; there's no NavMeshObstacle carve to lean on.
- **The escape hatch is a kit template too (F80).** `InteractableKit.escapeHatch` (optional slot, built by **LIGHTS OUT > Build > Interactables**) is a double-leaf trapdoor made of two Alchemist `WoodDoor01` leaves over a `Glow` slab. `MazeEscape.BuildHatch` clones it, gives `Glow` the runtime `HatchGlow` material (so `ApplyLockLook`'s green/red still works) and swings the `LidL`/`LidR` children about their local Z: shut while padlocked, ajar (16°) once usable, thrown open (100°) on entry. With the trapdoor present, stepping on the hatch runs `MazeEscape.EnterHatch` instead of the instant `CompleteEscape`: freeze, leaves open, the player eases over the opening looking down (0.75 s), then `FloorCleared` starts the blackout while they are lowered `dropStartDepth` through it (0.45 s); `_entering` holds the timer and trigger meanwhile, and the routine bails if a capture starts first. A black `Pit` inset makes the open hatch read as a hole. Empty slot = the old glowing slab and instant drop. The Lift variant is still primitives.
- **`MazeDoor._open` is intent, set when a slide starts, not when it ends.** It used to flip only at the end of the slide coroutine, so mid-slide every reader saw a stale value: `CheckBash` re-bashed a door that was already rolling up every frame (restarting the slide and renewing `AIFollower.Stall` forever — the hunter froze for good in front of a shutter that looked open), and `Unlock`/`AllStarsCollected` arriving while a bashed door rolled back down did nothing and left it shut but `_permanentlyOpen`. The physical state is the panel offset (`_blocker.enabled = _panelOffset < 2`). Doorway-occupied checks read the whole `DoorBreakers` registry (`BreakerInDoorway`), so a shutter never closes on the Stalker either, and a bash-hold that expires with someone in the gap retries every 0.5 s instead of giving up.
- **E has two owners now (F72).** `PlayerInteractor` (camera spherecast, `IInteractable`) is the default; `Locker` is the one holdout with its own E handling, and only because it predates this slice — new hideable/interactable things should implement `IInteractable`, not copy `Locker`'s pattern. `PlayerHud.SetFocusPrompt` always wins over `SetPrompt` while set.
- **New visible models are `InteractableKit` templates, not primitives at runtime.** Built once by **LIGHTS OUT > Build > Interactables** (`Assets/Editor/InteractableKitBuilder.cs`, build-missing-only by default so later slices can add their own slots safely); `MazeGenerator`'s various `Build*` passes clone them and log an error (naming the menu item) with no fallback if the kit or a slot is missing.
- **F74's new statics follow the same reset rule.** `RunRules` (current rule/name/description/multipliers) and `LoreArchive` (read note ids) both have a `[RuntimeInitializeOnLoadMethod(SubsystemRegistration)]` reset; `LoreArchive` is also cleared in `GameFlow.ReturnToMenu` (campaign-scoped, like `PlayerWallet`) while `RunRules` is recomputed every floor by `ApplyFloorProfile` regardless (still cleared there too, for cleanliness). `ThrowController`'s carried count and `Lantern`'s carried state are deliberately **not** statics — they're instance fields on components a scene reload naturally recreates, which is what makes them reset "for free" without touching this rule.
- **F87's statics follow the same reset rule.** `ContractState` (active contract, floor, the two offers, salesman line) has a `[RuntimeInitializeOnLoadMethod(SubsystemRegistration)]` reset and is cleared in `GameFlow.ReturnToMenu`. It is saved in `SaveData` as `contractActivePlus1` / `contractFloor` / `contractOfferAPlus1` / `contractOfferBPlus1` (ids stored +1, so a pre-F87 save - fields missing, read as 0 - means "none"; `SaveSystem.Version` was not bumped). `GameFlow.IsInIntake` is reset in `Reload`, `ResetStatics` and (through `Reload`) `ReturnToMenu`; `IntakeRoom.Active` is a scene-scoped reference cleared in `OnDestroy`. `ContractTracker` and `ThrowController`'s carried count are instance state and reset by a scene reload; its three static-event subscriptions (`LoreNote.Read`, `Stalker.PlayerTouched`, `ThrowableItem.HunterInvestigated`) unsubscribe in `OnDestroy`.
- **`FloorProfile.Objective` is a flag set now (F77), not the single `FloorObjective` value it used to be.** `Objective.Stars` is gone — stars are always present — so test a mechanic with `profile.Has(Objective.Lockdown/Blackout/KeyHunt)`, never equality against `Objectives`. `GameFlow.RolledObjectives` (the previous floor's rolled pair, so two consecutive floors never repeat) follows the same static-reset rule as everything else in the first Gotcha above: reset in `ResetStatics` and `ReturnToMenu`. `RunRules.HashSeedFloor` is `internal` (not `private`) specifically so `FloorProfile.RollObjectives` can reuse it with its own salt — the two rolls are deliberately independent draws from the same seed, not the same draw read twice. `+18` is `BuildKeys`' RNG offset — the next free one is `+19`. The padlock itself (locked hatch/lift, red glow, wayfinding retarget to the nearest missing key) lives entirely in `MazeEscape`, not in `GameOutcome` or `GameManager`.

- **Any new direct key-reader must also OR in the `TouchInput` facade (F76).** The pattern that bit the first seven readers before `TouchInput` existed - a bare `Keyboard.current`/`Gamepad.current` check with no touch equivalent - silently strands tablet players on that one action. `TouchInput.Pressed`/`Held`/`Released` cost nothing to add next to the existing check even if you never wire up a button for it. Also: `TouchInput.Pressed`/`Released` intentionally lag `SetHeld` by one frame (see the Touch/tablet bullet above) - don't "simplify" that to same-frame, it exists to make every reader see the edge exactly once regardless of execution order.
